# S0.5 — Wiring the API to the frontend

> **Status:** plan. Implement task-by-task, each ending green.

**Goal:** Replace the mock seam with real HTTP for the two modules that have a
backend — auth and vehicles — seed the database with the fleet the mocks
already describe, and get the whole thing running against hosted Postgres.

**Why now:** `WORK_SPLIT.md` promises that finishing a backend stage changes
*"exactly one frontend file"*. That promise assumes fetch plumbing that has
never existed: `lib/api/client.ts` exports `delay()` and `paginate()` and
nothing else, and there is not one `fetch` call in `src/`. S0 was meant to
deliver this and only did the backend half. Every stage after S1 inherits the
same blocker, so it is worth building once, now, rather than twice later.

## The shape of the deployment

Netlify cannot run a Spring Boot application — it hosts static assets and
Node/Go serverless functions only. So "host it on Netlify" splits into three:

| Piece | Where | Why |
|---|---|---|
| Frontend (Vite build) | **Netlify** | static assets, which is what Netlify is for |
| Postgres | **Netlify DB (Neon)** | a standard connection string, reachable from anywhere |
| Spring Boot API | **Render** (or Fly.io / Railway) | a long-running JVM needs a host that runs processes |

Netlify DB is Neon under the covers and hands out an ordinary
`postgresql://…?sslmode=require` URL, so the API connects to it the same way it
connects to the local container. Nothing in the application changes.

## Two things about Neon that will bite if ignored

**It scales to zero and caps connections.** HikariCP holding a large idle pool
against a serverless Postgres is the wrong shape. Use the *pooled* connection
string and a small pool (`maximum-pool-size: 5`), and expect a cold first
request.

**Transaction pooling and RLS.** Tenant isolation works by
`set_config('app.tenant_id', ?, true)` — the `true` makes it `SET LOCAL`,
scoped to the transaction. That is safe under transaction pooling. It would not
be safe if it were session-scoped, so this must stay `true` forever. A change
there silently leaks one tenant's rows into another's request.

## What can actually be wired

Only auth and vehicles have a backend. Riders, service jobs, assignments,
payments, users and audit are still S2–S6 and do not exist.

| Section | Backend? | This plan |
|---|---|---|
| Login | S0 ✅ | **wired** |
| Fleet → Vehicles | S1 ✅ | **wired** |
| Operations, Service, Riders, Money, Admin | ✗ | stay on mocks |

So the seam's first requirement is **coexistence**: real and mock modules side
by side in one running app. That is not a transitional hack — it is the steady
state until S6 lands, and it is exactly what S2 will need next.

### How coexistence works

`vehicles.ts` becomes a two-line facade over `vehicles.live.ts` and
`vehicles.mock.ts`, picking one at module load:

```ts
const impl = IS_LIVE ? live : mock;
export const listVehicles = impl.listVehicles;
```

No screen changes. No other API module changes. `vitest` sets no API base, so
tests keep resolving to the mocks and keep passing unchanged. When S2 lands,
Abhiram does the same two-line facade for `riders.ts` and nothing else moves.

`IS_LIVE` is `VITE_API_BASE` being set. One variable, no separate flag to get
out of sync: if you pointed the app at an API, you meant it.

## Not in this plan

- **The other five sections.** They have no backend to talk to.
- **`.xlsx` import** (the `excel` module in `ARCHITECTURE.md`). Separate.
- **`currentRiderId` / `currentRiderName`.** `VehicleResponse` hardcodes these
  `null` because assignments are S5. The UI already handles null. It will keep
  showing a blank rider column until S5, and that is correct, not a bug.

### Task 1: The request seam

**Files:** `lib/api/client.ts`, new `lib/api/tokens.ts`, test
`lib/api/client.test.ts`

`request()` does JSON, throws `ApiError` built from the backend's
`ApiErrorResponse` (preserving `field`, which the forms already read), and on a
401 refreshes once and retries.

**Single-flight refresh.** A dashboard fires several queries at once; on an
expired token they would each start their own refresh, and because refresh
tokens **rotate**, the second one to arrive is using a token the first already
burned — every parallel request after the first fails and the user is thrown to
the login screen mid-session. So a refresh in progress is a shared promise that
every waiting caller awaits.

**Token storage.** `sessionStorage`, not `localStorage`: this is a fleet
operations console, and a token that dies with the tab is the right default.
It also survives reload, which the current fake session already does.

**Tests:** success; error body → `ApiError` with `field`; 401 → refresh → retry
succeeds; one refresh for three concurrent 401s; failed refresh clears the
session.

### Task 2: The auth module

**Files:** new `lib/api/auth.ts`

`login`, `refresh`, `logout`, `me` against `/api/v1/auth/*`. `AuthResponse` is
`{ accessToken, refreshToken, user }` — the user comes back with login, so the
UI renders the session without a second round trip.

### Task 3: `tenantName` on the user

**Files:** `user/UserResponse.java`, `auth/AuthService.java`, auth tests

The rail hardcodes `tenant: 'G1 Mobility Rentals'`. With real login that string
is a lie for any other tenant. Add `tenantName` to `UserResponse` — additive,
so nothing existing breaks.

### Task 4: The real session

**Files:** `app/session.tsx`, `app/sessionContext.ts`

Restores from stored tokens on load, calls `/auth/me` to confirm, exposes
`signIn(email, password)` and a `signOut` that calls the API so the refresh
token is actually revoked.

**The persona switch goes away in live mode.** It exists so a walkthrough can
show what each role sees without logging in. Under real auth the role comes
from a signed token and cannot be switched client-side — leaving a control that
appears to change your role but does not would be worse than removing it. It
stays in mock mode, where it still does exactly what it claims.

### Task 5: The login page

**Files:** `pages/Login.tsx`

Real submit, disabled while pending, and the 401 surfaced as
*"Email or password is incorrect"*. Today it ignores what you type entirely.

### Task 6: The vehicles module

**Files:** `lib/api/vehicles.live.ts` (new), `vehicles.mock.ts` (renamed from
`vehicles.ts`), `vehicles.ts` (facade)

All nine endpoints. Query params map straight across; `ALL` and blank are
already normalised server-side, so the client sends what the screen holds.

### Task 7: Export the fleet as a seed

**Files:** `frontend/app/scripts/export-fleet-seed.mjs`,
`backend/src/main/resources/db/seed/fleet.csv`

The mock fleet is 137 bikes generated in TypeScript with a deliberate state
mix (97 `DEPLOYED`, 22 `READY_TO_DEPLOY`, 9 `UNDER_REPAIR`, …) and weighted
hubs. Rather than reimplement that distribution in Java and let the two drift,
a script exports the generated fleet to CSV in the import format the backend
already parses.

Seeding from the same data the mocks draw means the wired screen and the mock
screen show the **same fleet** — so any difference after the swap is a real
defect, not a data difference. That is the whole point.

### Task 8: Load the seed

**Files:** `platform/DevFleetSeeder.java`

Idempotent, and gated on a property that only the local profile sets — the same
shape as `BootstrapData`, and for the same reason: a deployed environment that
already has bikes must not get 137 fake ones. Skips if the tenant has any
vehicle already.

### Task 9: Verify end to end

Boot Postgres and the API, point the frontend at it, log in with a real
credential, and confirm the vehicle list, facets, filters, detail and
transitions all read from the database.

### Task 10: Deploy configuration

**Files:** `frontend/app/netlify.toml`, `render.yaml`, `docs/backend/DEPLOY.md`
