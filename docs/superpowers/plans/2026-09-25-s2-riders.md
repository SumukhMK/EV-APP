# S2 — Riders Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the rider register — onboard a rider (identity, contact, address, commercial), list and search the register, and read a rider's record. Aadhaar is stored encrypted at rest.

**Architecture:** One Spring module, `com.evrental.rider`, on the S0 floor. One table behind Flyway (`V008__riders.sql`), row-level security through V001's `enable_tenant_rls` helper. The register stores exactly what the frontend contract (`frontend/app/src/types/rider.ts`) exposes; identity/contact/address fields captured at the counter are not persisted (matching the mock), and Aadhaar is stored encrypted at rest (AES-256-GCM, key from the `AADHAAR_ENCRYPTION_KEY` environment variable — never on the wire, never in session storage client-side). `currentVehicleId` is deliberately absent — it is a property of the open assignment, which S5 owns (the same reasoning `Vehicle.java` applies to `currentRiderId`).

**Tech Stack:** Spring Boot 4.1.1, Java 21, Postgres 16, Flyway, JPA, Testcontainers.

**Spec:** `docs/BUILD.md` S2 row ("Riders: CRUD, KYC, Aadhaar masking — done when: Create rider, masked Aadhaar"), the contract in `frontend/app/src/types/rider.ts`, and the mock behaviour in `frontend/app/src/lib/api/riders.ts` + `frontend/app/src/mocks/riders.ts`. RBAC from `docs/backend/RBAC.md` (Riders section = SA/FA/FS; SERVICE_MANAGER never sees it).

## Global Constraints

- Migration file is **`V008__riders.sql`** (next free number; V003–V007 are taken).
- RLS is added with `SELECT enable_tenant_rls('riders')`, **not** a hand-written policy (migration README rule 1).
- Money is paise, `BIGINT`, never a float. The wire already carries paise — the onboard form converts rupees→paise (`OnboardRider.tsx`: `planAmount: values.planRupees * 100`), so the backend stores what it receives; no conversion at this boundary.
- Every list is paginated through `PageResponse`. No endpoint returns everything.
- Errors leave through `NotFoundException` (404), `ConflictException` (409), `ValidationException` (422). Nothing builds an error by hand.
- Role gates are `@PreAuthorize` on the controller, matching `docs/backend/RBAC.md`: **all rider endpoints are SA/FA/FS** — SERVICE_MANAGER gets 403 everywhere on the register.
- Nothing here filters by tenant. RLS does that on the transaction the TenantFilter opened (same as `VehicleService`/`UserService`).
- Aadhaar is stored encrypted at rest (`AadhaarCipher`, AES-256-GCM, key from `AADHAAR_ENCRYPTION_KEY` — no default, so a deployment that forgets it fails at boot). The API never returns it; the frontend keeps it in form state only, never in session storage.
- The register stores only what `Rider` exposes. Addresses, PAN, driving licence, coordinates and `platformRiderId` are captured at the counter but not persisted — the mock discards them too, no screen reads them back, and PAN/DL are PII nothing consumes. Raise a type change if a screen needs them.

### Decisions agreed with Ashok (2026-09-26)

1. **Aadhaar:** stored encrypted at rest (AES-256-GCM, key from the `AADHAAR_ENCRYPTION_KEY` env var — never in the DB, never on the wire, never in session storage client-side). **Superseded 2026-09-26** by Ashok's request to store it; the original ruling discarded it entirely.
2. **Rider id on the wire:** the UUID. The mock's `R03`-style ids are a facade concern; `RiderDetail` treats `id` as an opaque string.
3. **Uniqueness:** phone unique per tenant (409 naming `phone`). No Aadhaar duplicate detection.
4. **`currentVehicleId`:** not stored. `RiderResponse.currentVehicleId` is always `null` until S5 owns assignments. The `vehicleState` list filter therefore matches nothing in live mode (short-circuits to an empty page) — no rider holds a bike yet.
5. **`listAssignableRiders` / `listAssignedRiders`:** implemented in S2. Assignable = ACTIVE riders; assigned = empty until S5.
6. **`listRiderPayments`:** the endpoint exists and returns an empty list; S6's second half computes real periods.
7. **`paymentStatus`:** always `'PENDING'` until S6 derives it from the current period.
8. **`depositPaid`:** discarded. `depositHeld = depositPlan` (the mock's rule: the register holds the deposit plan, which is what a deboard settles against).
9. **KYC:** onboard creates ACTIVE + KYC PENDING. No verify/reject endpoint — nothing in the product changes `kycStatus` yet. The four verification flags are stored for audit.
10. **Foreign keys:** V008 adds `service_jobs.rider_id → riders(id)` and `rider_charges.rider_id → riders(id)`, the FKs V006/V007 deliberately left off. Consequence: the S4/S6 tests that opened jobs with `UUID.randomUUID()` rider ids must seed a real rider first (Task 9).
11. **Dev seed:** `DevFleetSeeder` also seeds the ten designed riders from the mock (same names/phones/plans/days), so wired and mock registers agree.
12. **Update endpoint:** not built — no edit screen exists. Create + read + list only.
13. **Frontend facade swap:** not part of S2. `riders.ts` keeps serving mocks until S2+S5+S6 are all live (the S4 swap is blocked on the same three).

### Deliberate divergences from the mock

- **Search does not match `r.id`.** The mock matches `R03`-style ids; live ids are UUIDs nobody types. Search matches name, phone and platform.
- **`paymentStatus` is always PENDING.** The mock fabricates PAID/PARTIAL/OVERDUE; S6 derives the real value.
- **`vehicleState` filter matches nothing.** The mock pairs riders with bikes; live riders hold no bike until S5.
- **Seed riders show PENDING.** The mock's designed riders carry PAID/PARTIAL/OVERDUE; S2 cannot derive those.

## Review Focus

Five things the contract implies but does not give a test:

1. **A duplicate phone.** The mock throws 409 naming `phone`; the backend must too, before the unique index turns it into a constraint violation.
2. **A rider id that is another tenant's.** RLS hides the row, so `GET /riders/{id}` must 404 rather than leak.
3. **The `vehicleState` filter.** No rider holds a bike until S5; the filter must return an empty page, not ignore the filter or error.
4. **SERVICE_MANAGER on the register.** RBAC.md says the Riders section is SA/FA/FS; SM must get 403 on every rider endpoint.
5. **The FKs V006/V007 left off.** A service job or a charge that names a rider must name a real one — and the existing S4/S6 tests must keep passing with real riders seeded.

## What shipped (2026-09-26)

**Migration** — `V008__riders.sql`: the `riders` table (UUID PK, tenant FK, name, phone, status/kyc_status/billing_day/payment_day/payment_mode CHECKs, money CHECKs, platform, onboarded_on, four verification flags, created/updated), `idx_riders_phone` unique per tenant, `idx_riders_status`, tenant RLS, and the two FKs V006/V007 deliberately left off: `service_jobs.rider_id → riders(id)` and `rider_charges.rider_id → riders(id)`.

**Module** — `com.evrental.rider`: `RiderStatus`/`KycStatus`/`BillingDay`/`PaymentDay`/`PaymentMode` (labels match `lib/labels.ts`), `Rider` entity (no `currentVehicleId`/`paymentStatus` — S5/S6 own those), `RiderRepository` (lower() phone lookup, optional-param search, status counts), `OnboardRiderRequest` + nested `RiderVerification` (aadhaar/phone/name/money/address validation), `RiderResponse.from()` (`currentVehicleId` null, `paymentStatus` "PENDING"), `RiderQuery`, `RiderService` (onboard → ACTIVE + KYC PENDING, deposit = plan, 409 on duplicate phone; search/facets short-circuit on `vehicleState`; 404 via `NotFoundException`), `RiderController` (POST `/api/v1/riders` 201; GET list/facets/assignable/assigned/{id}; SA/FA/FS on every method).

**Payment seam** — `RiderPaymentRow` + `RiderPaymentController` in `com.evrental.payment`: `GET /api/v1/payments/riders/{riderId}/periods` validates the rider then returns an empty list until S6's second half.

**Seeder** — `DevFleetSeeder.seedRiders`: the ten designed riders from `mocks/riders.ts` (ACTIVE/VERIFIED, onboarded 2026-04-08), idempotent, same transaction as the vehicle seed. Each carries a deterministic fake Aadhaar (phone + "01"), stored encrypted.

**Aadhaar at rest** — `AadhaarCipher` in `com.evrental.common`: AES-256-GCM, a fresh random 12-byte IV per value, 128-bit tag, key from `AADHAAR_ENCRYPTION_KEY` (no default in `application.yml` — a deployment that forgets it fails at boot; the test profile carries a throwaway key). `V008` gains `aadhaar_encrypted TEXT NOT NULL`; `RiderService.onboard` encrypts before save; `RiderResponse` has no aadhaar field, so the wire cannot leak it. Frontend already complies: the number lives in react-hook-form state only — `sessionStorage` holds just the JWT and a session flag.

**Tests** — `RiderTestBase` (own tenants `1000…`/`2000…`, riders, token helpers), `RiderSchemaTest` (8: per-tenant phone uniqueness, RLS, CHECKs, the V008 FKs, `aadhaar_encrypted` NOT NULL), `RiderOnboardTest` (8: the full shape — response never returns the Aadhaar — duplicate phone, cross-tenant phone, malformed phone/aadhaar/plan, verification flags stored, Aadhaar stored encrypted and round-tripping), `RiderReadTest` (13), `RiderRbacTest` (3), `AadhaarCipherTest` (7: round-trip, random IV, ciphertext never contains the number, wrong key, tamper, unsupported format, short key). `ServiceJobTestBase` seeds a rider (`RIDER_ID`) and the four service tests use it; its cleanup re-runs the whole seed once on a fresh transaction when a late async charge fails the `service_jobs` delete (the FK violation aborts the first transaction, so the retry cannot run inside it). `VehicleTestBase`'s rival tenant slug made unique (`rival-vehicles-co`) so bases never collide on `idx_tenants_slug` regardless of class order.

**Verify** — `mvnw test`: 250/250 green (211 baseline + 39 new).

## What is deliberately not done

**The frontend swap.** `lib/api/riders.ts` still serves mocks. Flipping it needs S2 (this stage), S5 (assignments — the bike column and `vehicleState` filter), and S6's second half (payment periods and `paymentStatus`) all live; the S4 swap is blocked on the same three. Recorded in WORK_SPLIT.md.

**KYC verification.** No verify/reject endpoint — nothing in the product changes `kycStatus` after onboarding. The four OTP flags are stored so a future verification step has a trail.

**Rider update.** No edit screen exists; "CRUD" ships as create + read + list. Add update when the screen does.

**Aadhaar on the wire.** The register stores the number encrypted at rest but never returns it — not even masked. Nothing reads it back until a KYC verification step needs to.
